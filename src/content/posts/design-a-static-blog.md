> **示例内容**：本篇用于本地预览、测试目录和代码排版，不是作者真实经验的陈述，正式构建不会发布。

有些问题解决之后，很快就会忘记当时是怎么想的。给它留下一份记录，下次遇到类似的事情，便不用再从空白开始。

这个示例介绍一种简单的组织方式：让文章、项目和主题彼此关联，让记录能在日后被找到。

## 先把内容保存下来

Markdown 的优点，是不需要先考虑页面长什么样。标题、正文、列表和代码都可以存放在普通文本文件里，再交给静态站点生成器处理。

一篇文章可以带着一小段描述信息：

```yaml
title: '一篇真实的技术记录'
description: '说明解决了什么问题，以及读者能从中获得什么。'
slug: 'a-real-technical-note'
publishedAt: '2026-10-18'
category: '工程实践'
tags: ['TypeScript']
draft: true
```

`draft: true` 的意思很直接：内容还没有准备好，先不要发布。写作可以慢慢来，公开内容则需要一个明确的边界。

## 在记录之间建立连接

### 分类与标签各司其职

分类提供一个相对宽泛的阅读入口，例如“工程实践”或“生活随笔”。标签则标出更具体的线索，例如 Astro、TypeScript、阅读。

不必在第一天就定义所有主题。先写文章，再让分类从实际内容里自然生长。

### 文章和项目双向关联

文章可以解释为什么这样实现，仓库则保留可以继续验证的代码。两者通过配置关联，不需要把其他项目的源码复制进博客。

## 让发布过程可以复现

```ts
type Note = {
  title: string;
  draft: boolean;
};

const readyToPublish = (note: Note) => !note.draft;
```

代码块应该容易阅读，也能方便复制。内容检查、构建和站内链接验证，则在发布前发现可以确定的问题。

| 环节     | 关注点                     |
| -------- | -------------------------- |
| 内容校验 | 必填字段、日期与稳定链接   |
| 构建     | 可重复生成静态页面         |
| 产物检查 | 元数据、站内链接、草稿隔离 |

## 给未来的自己留一点线索

记录不需要每次都面面俱到。写清楚问题、尝试、结论和可查证的来源，往往比追求一篇看起来“完整”的文章更有用。

从一个小问题开始，逐渐把知识连接起来。

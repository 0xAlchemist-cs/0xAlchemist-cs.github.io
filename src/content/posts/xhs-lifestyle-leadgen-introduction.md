让 AI 写一篇小红书文案并不难。真正难的是下一步：这篇适合现在发吗？与前几篇是不是太像？手上的经历够不够支撑这个选题？有人来问细节时，我能提供什么有用的帮助？

我把这些判断整理成了 [xhs-lifestyle-leadgen](https://github.com/0xAlchemist-cs/xhs-lifestyle-leadgen)。它是一套面向 Agent 的内容运营 Skill，把账号定位、资料调研、内容分层、发布决策和复盘连起来，重点服务于希望保留个人表达、同时接触有具体需求读者的账号。

目前仓库以旅行场景为主要例子。它交付的是工作方法和参考文档，执行依赖所使用的 Agent、浏览器工具与用户提供的真实素材。

## 先确认有什么可写，再决定写成什么

项目把真实性放在选题之前：没有亲历的事情，就用资料整理的视角表达；没有提供的价格、场景或体验，就留下需要补充素材的位置。

例如，研究过一条路线，可以写自己的比较过程，但不能因此写成“我上次走这条线时”。AI 擅长补全细节，在个人内容里，这种能力反而需要约束。

因此，流程从定位访谈开始，先确定账号的兴趣、已有经历、可以公开的素材，以及不愿涉及的内容。后面的建议都应当建立在这些条件上。

```text
定位与素材边界 → 真实资料调研 → 分层选题池
              → 推荐下一篇 → 用户确认后出稿
              → 数据回填 → 调整后续选题
```

对我来说，这比一次生成十个看似吸引人的标题更重要。它让 AI 先理解“这个人能写什么”，而不是把任何人都套进同一套文案。

## 用内容池区分表达目的

项目将日常生活记录放入 A 池，将旅行相关内容放入 B 池，再按读者需求细分：

| 内容类型         | 回答什么问题                 | 旅行场景示例               |
| ---------------- | ---------------------------- | -------------------------- |
| A：生活记录      | 我最近在过怎样的生活？       | 真实的周末安排、工作与兴趣 |
| B · L1：兴趣表达 | 我为什么对这件事感兴趣？     | 最近想去的地方与原因       |
| B · L2：信息整理 | 我查到了什么，怎样比较？     | 路线、交通和行前资料整理   |
| B · L3：具体决策 | 面对预算或选择，该考虑什么？ | 不同出行方式的成本与取舍   |

这些例子用于说明分类，实际写作仍需要对应素材。

Skill 建议观察最近十篇的分布，并为高意向内容设置间隔，避免连续围绕价格、选择和咨询发帖。文档中的比例与间隔是项目采用的运营起点，适合结合账号反馈调整。

这种分类的用途是帮助取舍：一篇日常记录可能互动不高，但仍然值得写；一篇决策型内容则应当有足够的信息，真正回答准备行动的人关心的问题。

## “给我下一篇”之前，先看最近发生了什么

发布决策是这个项目里我最看重的部分。

当用户说“给我下一篇”，Agent 需要先检查最近十篇的类型分布、相邻内容是否重复、主页内容密度、已有数据，以及当前更适合服务哪类读者，再给出一个推荐。

输出包括推荐类型、理由、具体选题、标题方向和预计吸引的人群。用户确认后，才进入正文写作。

例如，最近已经连续写了两篇旅行资料整理，手上又没有新的真实体验，与其继续生产一篇相似攻略，不如先选一个已有生活素材。反过来，如果评论中反复出现同一个预算问题，就可以判断是否值得认真整理一篇回答。

这里的关键是让历史信息影响下一次选择。每次打开对话，都从零开始问“有什么爆款选题”，很难形成稳定的内容方向。

## 调研读者的问题，复盘回答有没有用

调研文档要求结合真实的站内内容与评论分析需求，区分点赞、收藏和提问分别代表什么。与其只找一篇点赞很高的笔记，更值得看评论里反复出现的具体疑问，以及自己有没有能力补充答案。

拿不到站内数据时，结论需要说明资料范围，不能把猜测写成已经验证的趋势。调研依赖用户有权使用的账号和浏览器能力，仓库没有自带一个独立的数据采集服务。

发布后，再把浏览、收藏、评论、关注和咨询等数据回填到追踪表，按一组内容复盘：哪类主题值得继续？读者收藏了什么？提问是否更具体？下一篇需要补足什么？

仓库也包含对平台推荐机制的解释和一些数值判断。本文采用其中可执行的选题与记录方法；账号表现是否改善，需要在持续记录中观察，不能仅凭这些规则推断。运营目标中的“获客”也应落实为有价值的答疑与真实可交付的服务，涉及商业合作时应清楚说明。

## 让互动回到具体回答

评论区部分强调：只回答自己能够回答的问题，不群发私信，不批量复制评论，也不把虚构经历当作建立信任的工具。

一个有用的回答，可以是说明比较条件、指出遗漏的信息，或者坦诚表示自己没有体验过。它不需要每次都导向咨询。

如果读者主动提出进一步需求，还需要先确认自己是否有相应资源或服务能力。没有，就停留在资料分享和筛选建议。这也是项目把“能交付什么”纳入流程的原因。

## 怎样开始使用

将仓库放入所用 Agent 支持的 Skills 目录后，可以从一个带上下文的请求开始：

> 我想持续记录自己的生活，也整理旅行资料。请先问清我的真实经历、可用素材与表达边界，再建立内容池。推荐下一篇时，说明为什么现在适合写它，等我确认再出稿。

比起直接要求“帮我写一篇爆款”，这样的输入能让 Skill 使用到定位、选择和确认环节。

当前版本的 `SKILL.md` 有一处引用了尚未随仓库提供的内容池文件；实际分类与决策规则集中在 `references/decision-rules.md`，阅读时可以从这里进入。

## 把判断留下来，才方便下次继续

这个项目尝试保存的，是一次次内容选择背后的判断：为什么写、凭什么写、希望回答谁，以及发布后得到了什么反馈。

当这些信息能够被下一轮写作继续使用，AI 才更像一个了解上下文的协作者。文章仍然由真实素材支撑，方向也仍然由自己决定。
